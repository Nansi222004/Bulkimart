## C. End-to-end flows and operational prerequisites

### Legal Services

Home → Services banner → `/services` → legal capabilities → LegalServices → published customer catalogue → View service → `/legal-services/:id` → requirements/review → authenticated multipart application. Backend submission checks `LEGAL_SERVICES_SUBMISSIONS_ENABLED`, named `legal_customer_key_unique` index, current form/service versions, answers/files and transactional creation (`legalServices.controller.js:56-84`). Submission collects no payment. Admin review/confirmed quotation, private follow-up, payment verification and authorized provider work are subsequent independent steps. Account → My Legal Service Requests is another history entry that remains when the hub catalogue is disabled.

Independent `/legal-services` bypasses the hub capability precheck and directly requests the catalogue. When disabled, it displays the backend error + Reload latest, and may also show “No eligible services available.” When enabled but genuinely empty, it shows that empty state. Failed loads stop loading and expose retry; previous list items can remain visible after a later failed request. Successful malformed envelopes are not comprehensively schema-validated before items.map/meta use.

Flags (`backend/services/legalPolicy.service.js:7-15`): `LEGAL_SERVICES_{CATALOGUE,SUBMISSIONS,FULFILMENT,PAYMENTS,REFUNDS,PAYOUTS}_ENABLED`, each strict string true, otherwise false. Non-catalogue operations reject exact production NODE_ENV/DEPLOYMENT_ENV; unlike parcel, this predicate does not normalize aliases. Gateway requires Razorpay test mode/test key. The capability DTO exposes catalogue/submissions only; the customer form does not use submissions to disable itself or expose production blocking before submission. Backend remains authoritative, but catalogue visibility alone does not imply intake works.

### Send a Parcel

Home → Services banner → `/services` parcel card → independent parcel capabilities → effective policy (only if booking prerequisites pass) → `/parcel-delivery/book` → buyer session → capabilities/catalogue → manual/saved pickup/dropoff coordinates and parcel details → POST quote → backend approved area/restrictions, getRoute and policy fare → quote/terms/payment-method confirmation → POST booking → separate parcel lifecycle. No legal catalogue entries, legal index, legal flags or GST request are required.

Flags (`backend/services/parcelPolicy.service.js:5-14`): `PARCEL_DELIVERY_{CATALOGUE,BOOKING,ONLINE_PAYMENT,PAY_DRIVER,AUTO_ASSIGNMENT,ADMIN_FALLBACK,FULFILMENT,REFUNDS}_ENABLED`. Catalogue is discovery/policy visibility, not authorization to book. Booking additionally enforces selected payment method and dispatch gates before accepting an obligation (`parcelWorkflow.service.js:40-44`). Production/prod/deployment-production values, trimmed and case-normalized in either runtime variable, block non-catalogue operations. HTTP non-GET mutation middleware also blocks production. Online gateway additionally requires PAYMENT_GATEWAY=razorpay and isolated Razorpay test credentials. No settings were changed.

Policy readiness is only effectiveAt at the public endpoint; it does not certify route provider health, gateway credentials, database readiness or available riders. `backend/services/maps.service.js:13-22` implements only authorized mock routes and throws for real directions; `quoteParcel` converts that to verified-route-provider-unavailable 503. Thus even a visible Book a Parcel link is not proof that live quoting works. Approved policy/pricing/terms/service areas, transaction-capable DB, operational/rider readiness and separate financial approvals are additional prerequisites. Existing assignment/admin fallback, parcel finance separation and payout blockers are outside this UI audit's activation scope.

History → private list → row → tracking with status/timeline/codes and existing payment/cancellation actions. Existing reads can remain useful while new booking is disabled. Source shows no automatic coupling to shopping COD, checkout or legal payments in these customer navigation changes.

## E. Recommended next steps (not implemented)

1. Decide whether Legal Services and Send a Parcel need separate home entries. If so, reuse existing routes and components; no backend rebuild or legal dependency is needed. Current combined hub is an explicit UI arrangement only.
2. First fix parcel tracking failure fallthrough and separate history errors from successful empty history. Add focused regressions covering failures after successful loads as well as initial failures.
3. Align direct booking/detail availability messages with backend submission/booking prerequisites; retain independent history access and server guards. Do not activate flags merely to improve discovery.
4. Keep legal catalogue publication separate from legal intake/payment approval. Read-only inspect actual deployed capabilities, published/customer records, required index/storage/transaction readiness with authorized operational access before any activation decision.
5. For parcels, investigate/implement authoritative directions under a separately approved scope before claiming live quotation readiness. Validate policy/dispatch/gateway readiness in isolated staging; do not replace directions with straight-line or mock fares.
6. Rerun actual customer journeys and mobile/desktop geometry in a working browser harness. Confirm bottom navigation and returning from standalone parcel workspace. Consider explicit invalid-route states and API envelope validation as small follow-up hardening tasks.
