# Admin Dashboard metric contract v1

Scope: all time, INR, business timezone Asia/Kolkata. No date filter or daily buckets. Calculations run in a read-only MongoDB snapshot transaction; asOf identifies the observation, not a bank reconciliation timestamp. No financial mutation or new accounting collection is introduced.

| Card | Definition / authoritative source | Treatment and coverage |
| --- | --- | --- |
| Total Order Value — gross completed | Sum valid `Order.pricing.totalAmount` for `status: delivered`, once per fulfilment Order | Gross original completed customer order value, **before subsequent refunds**. Price already includes checkout discounts and customer delivery/tip/donation. Returned/refunded/cancelled whole orders and in-progress orders excluded. Item Returns do not subtract from this deliberately gross measure. Payment failure/unverified COD does not remove an otherwise delivered order from a sales measure; it is not collections. Shared Payment amount is never summed here. Missing/invalid pricing makes the total unavailable, with valid-record subtotal identified separately. |
| Money Collected — net verified external order collections | Settled online Payment capture journal minus completed verified refunds; COD Order `codFinance` exact independent platform receipt minus evidenced completed manual refunds | Order payments only; exclude top-ups, advertising, parcel/legal/service/subscription/packaging purposes. Count a shared Payment capture once, not once per Order. Duplicate identical capture/refund IDs count once; conflicting IDs, refund projections, unmatched completed Returns, legacy paid-only metadata and cash disputes produce an incomplete total, never a confirmed zero. Pending/failed attempts without a settled capture contribute nothing. Captured funds on a later cancelled order remain collections until verified refunded. Wallet payments are internal transfers and are excluded, not new external receipts. COD collection/remittance reports without independent exact verification are excluded and disclosed. Excess/short/disputed cash needs reconciliation and is not recognized as order collections. This is verified gross capture less verified completed refunds, not provider bank settlement or new cash receipts from all business activities. |
| Bulkimart Revenue | Recognized platform-wide revenue is **unavailable**: the current merchandise commission account records allocation and has no approved platform-wide recognition/fee consolidation contract | Expose a clearly labelled net posted merchandise commission subtotal from `seller_ledger_entries.account: commission_revenue`, restricted to original v2 order-finance postings and compensating reversals. Taxes, seller/rider payable, gross merchandise, COD custody, delivery charges, Quick fee obligations, reservations and settlements are excluded. No rate multiplication or live commission recalculation. Missing postings/Return compensation and legacy coverage are disclosed. This subtotal is not presented as total recognized platform revenue. Other revenue domains and recognition timing require explicit accounting approval before a total can be enabled. |

Currency: Order/Payment/ledger rupees are validated with existing `moneyPaise`, converted once to safe integer paise; capture/refund/cash journals already use paise. API financial amounts are integer paise or null. UI divides by100 once. Invalid amounts fail coverage closed. Signed commission credit-minus-debit may be negative; sales and verified net collections cannot silently become negative.

Financial API requires authenticated Admin plus explicit `manage_finance`. Operational overview remains under existing Admin authorization, returns canonical recent-order amount (or null), approved seller count and separate pending count. No payment IDs, provider details, bank details or seller ledger rows are returned by the financial endpoint. Deprecated ambiguous `revenue` is null, not a guessed alias.

Unverified delivered COD is incomplete historical coverage; unfulfilled unverified COD is excluded. MongoDB5+ lookup support and a transaction-capable deployment are required. Verify an `orders.paymentId` index, the existing Return order index and a commission-account query index through a separately approved index review; this implementation does not create indexes or run migrations. All-time reads stream projected records, but production volume/transaction-duration testing is still required before rollout.

Historical evidence gaps never trigger writes, backfills, capture/provider lookups or reconciliation actions. A valid covered zero is distinct from an incomplete total or failed request. Permission/API/schema failures display unavailable/error with Retry; refreshing clears old financial values rather than silently presenting them as current.

Charts and `/admin/reports` remain unchanged and unimplemented. Future trends require the same financial definitions, explicit date boundaries, Asia/Kolkata buckets and `manage_finance`; report jobs/exports require separately scoped authorization and coverage disclosure.
