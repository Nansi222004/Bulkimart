# Coupon automation and threshold progress

The existing `Coupon` model and `evaluateCoupon` service remain the source of eligibility. An admin can opt a coupon into automatic application with `autoApply`; the default is `false`, including for existing documents. The customer can still enter or select a coupon manually. Only one code is active at a time; automatic selection never replaces a selected code and does not stack discounts.

`GET /api/coupons/available` uses a read-only, reconciled cart and returns usable offers plus threshold progress only when the coupon passes every existing check except its minimum-order gate. The engine's minimum is the **whole cart subtotal**; product, seller, and category scope controls which items receive the discount. The offer list keeps usable offers first, then orders by server-quoted saving, lower minimum, and code. Automatic selection takes its first applicable `autoApply` offer. Free delivery counts as the waived delivery charge, and is offered only when delivery would otherwise be charged. The frontend renders only the returned amounts and configured reward type.

Automatic application requires one retail delivery group. Grouped and wholesale checkout rejects coupons, so these baskets never receive an automatic coupon or a coupon-adjusted basket quote. The preview and cart read do not redeem anything. Checkout revalidates the code against live lines, and redemption rechecks validity and usage limits inside the order transaction. A newly applied code triggers one transient celebration after the priced cart confirms it; the animation respects reduced motion.

The existing `cdsMembersOnly` field has no verified membership source in the coupon evaluator. Such coupons are excluded from automatic selection and threshold advertising until that existing eligibility gap is resolved. Manual behavior is unchanged. The admin form still does not edit product, seller, or category scope arrays, though the model and API support them.
